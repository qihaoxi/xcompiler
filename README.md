## 项目目标

本项目旨在使用 **C 语言** 实现一个基于 LLVM 的小型编译器框架，并以“可逐步落地、可持续验证”为原则推进开发。

项目的长期愿景是构建一个具备完整编译流程的编译器系统，包括：

- 词法分析
- 语法分析
- AST 构建
- 语义分析
- 中间表示（IR）生成
- 对接 LLVM IR 后端
- 通过现有工具链生成目标文件或可执行文件

> 当前阶段不以“自研完整链接器”为首要目标，而是优先完成编译器前端与 LLVM IR 生成，并借助现有 LLVM/Clang 工具链完成后续流程。

## 开发路线图

### 阶段 1：最小可运行前端（MVP）

目标：实现一个可以处理简单源代码并输出 AST 或诊断信息的前端。

当前仓库已经先把工程骨架搭起来，并补上了一个可运行的“纯前端”闭环：lexer → parser → AST → semantic 校验。后续再逐步把运行时、IR 和后端接到这个前端输出上。

- 定义最小语言子集
- 实现词法分析器
- 实现语法分析器
- 构建 AST
- 提供基础错误定位与报错信息
- 编写基础测试用例

阶段验收标准：

- 可以正确解析若干示例程序
- 能输出结构化 AST 或语法错误信息

### 阶段 2：语义分析

目标：让编译器具备“理解程序含义”的能力。

- 建立符号表
- 实现作用域管理
- 实现基础类型检查
- 检测重复定义、未定义标识符等常见错误

阶段验收标准：

- 可以识别并报告典型语义错误
- 能为后续 IR 生成提供稳定输入

### 阶段 3：IR 生成

目标：将前端处理结果转换为中间表示。

- 设计项目内部 IR，或直接生成 LLVM IR
- 为表达式、变量、函数等核心结构生成 IR
- 保证生成结果可用于后续代码生成流程

阶段验收标准：

- 可以从合法程序生成正确的 IR
- 能覆盖基础算术、变量声明、函数调用等场景

### 阶段 4：LLVM 后端集成

目标：将编译结果接入 LLVM 工具链。

- 输出 `.ll` 或等价 LLVM IR 表示
- 通过 `llc`、`clang` 等工具生成目标文件或可执行文件
- 验证基础程序可以成功运行

阶段验收标准：

- 示例程序可以完成“源码 -> LLVM IR -> 可执行文件”的完整链路

### 阶段 5：工程化与扩展

目标：提升项目质量与可维护性。

- 补充单元测试与集成测试
- 完善 CMake 构建流程
- 增加示例程序与文档
- 逐步扩展语言特性
- 视需求评估优化、调试信息、增量编译或更完整工具链支持

## 当前建议范围

为了保证项目能尽快进入可验证状态，建议优先聚焦以下内容：

1. 语言最小子集设计
2. 词法分析与语法分析
3. AST 与基础语义分析
4. LLVM IR 生成
5. 基于现有工具链完成可执行文件生成

## 当前已搭好的 C 框架骨架

当前仓库已经按纯 C 方式搭好以下层次：

- `common`：状态码、诊断等通用基础
- `common/log.h`：统一日志接口（对外首选，导出 `XC_LOG_*` / `xc_log_*`）
- `src/common/xlog.h`：底层全功能日志实现；由 `log.c` 实例化共享状态，不再需要单独的 `xlog.c`
- `src/common/diagnostic.h`：诊断收集与错误列表
- `src/common/status.h`：内部状态码定义与转换
- `platform`：平台识别与后端偏好选择
- `api`：对外稳定入口
- `frontend/frontend.h`：前端模块总入口
- `src/frontend/common/common.h`：前端共享的源码视图与位置类型
- `src/frontend/ast/ast.h`：AST 结构接口
- `src/frontend/lexer/lexer.h`：词法层接口
- `src/frontend/parser/parser.h`：语法层接口
- `src/frontend/semantic/semantic.h`：语义分析上下文接口
- `ir`：中间表示接口（对外头仍保留在 `include/`）
- `driver`：流水线编排入口

其中，真正对外发布时只导出模块级公共头文件：`api/compiler.h`、`common/log.h`、`frontend/frontend.h`、`ir/ir.h`；其余头文件都与各自源码放在 `src/` 下。

这些模块当前以“骨架 + 最小可运行前端”为主：

- lexer 已可产出完整 token 流
- parser 已可把简单源代码汇总成平面 AST
- semantic 已可对 AST 做基本结构校验
- IR 与后端仍保留为后续扩展边界

## 编译检查策略

当前 CMake 默认启用较严格的检查风格，参考了 `raw-spofer-pel/polyglot-c` 的编译参数思路：

- 默认开启更严格的警告集
- 在支持的编译器上将警告视为错误
- 保留 file/macro prefix map，保证 `__FILE__` 输出相对路径
- 在 GNU/Clang 环境下尽量补齐栈保护相关选项

## 项目原则

- 先实现最小闭环，再逐步扩展
- 每个阶段都应具备可测试、可验证的输出
- 优先保证结构清晰、模块职责明确
- 避免在项目早期追求过大范围，导致难以收敛
